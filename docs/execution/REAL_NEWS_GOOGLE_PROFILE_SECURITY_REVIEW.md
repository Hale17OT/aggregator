## Concrete current contract findings

1. **Reuse the existing provider identity table.** packages/db/migrations/0001_identity.sql already defines auth_identities with UNIQUE(provider, subject), user FK and creation time. Canonicalize accepted Google issuer aliases to one configured provider identity key after cryptographic verification. Do not create a second Google account store. Preserve subject as an opaque case-sensitive string.
2. **Email continuity is a separate hazard.** users.email_normalized is UNIQUE; 0006 redeem_local_signin inserts/selects users by email for fictional example.test captured mail. Google must not invoke that account-selection path or resolve email collisions by assigning the existing user. Store minimal provider-email provenance separately; a Google-only user can retain null login email until an independently proved email method is linked. Never synthesize an email address as a substitute identity. Test identical email/different subject and existing captured-mail collision explicitly.
3. **Google sessions currently fail closed.** packages/domain/src/identity.ts and packages/contracts/src/member.ts accept only fixture/fixture-only or captured-mail/local-demo; 0006 constrains valid sessions and touch_fixture_session the same way. Extend all layers consistently with truthful provider assurance, retaining account status/version checks and null MFA. A new method string in HTTP alone cannot establish a usable session. Native transport/native_client_id restrictions in 0012 remain relevant; do not silently turn a native token into a cookie session or vice versa.
4. **Preserve the unit-of-work boundary.** packages/db/src/member.ts authenticates against a checked-out non-owner client; lookup_fixture_session locks account before session; touch establishes transaction-local identity only after bearer verification. PostgresMemberUnit returns only after COMMIT and discards ambiguous-commit clients. No Google key lookup, token verification network, publisher fetch or large export may enter that locked callback. Existing 1s lock/2s statement limits must not be extended to hide the recorded lock timeout.
5. **Preserve transport CSRF rules.** apps/api/src/member-http.ts rejects cookie/origin on native member routes, rejects Authorization on web member routes, and requires exact Origin plus synchronizer CSRF for cookie mutations. First-time Google exchange needs its own pre-auth binding; it cannot require an existing member CSRF token and cannot simply disable login CSRF. Existing browser handoff is not the newly required native Google path.
6. **Live policy is not presently enabled.** packages/editorial/policy.mjs requires scope.provenance fictional-test-declaration and exact item/kind/endpoint. Its extract purpose maps to allow_model, while media is generic. Add explicit reviewed real-grant provenance and justified use-specific decisions; neither forging fictional declarations nor deleting scope checks is acceptable. Reproduction, image, transcript, narration and video are not interchangeable with discovery, excerpt or synthesis. Existing repository checkPackage returns editorialApproved:false/publicationAllowed:false: retain that private boundary.
7. **Member saving needs a typed extension.** Existing bookmarks and repository DTOs reference article_id/saved_version_id. Real source items require their own valid typed identity/version relationship, not fabricated published article rows. Source schema already binds item/version/grant source ownership with composite FKs. Retain equivalent ownership for new save targets and tombstones.
8. **SDK implementation not established.** Current apps/mobile/pubspec.yaml inspected here contains no Google sign-in dependency. This pass cannot assert a supported nonce API. Resolve and inspect the selected plugin/platform implementation before accepting a native design; the runbook's singleton-initialization concern must be explicitly answered.

## Required security review checklist

### Per-attempt Google authentication and account continuity

- [ ] Server creates bounded, expiring attempts bound to initiating browser secret or native possession proof, exact client/audience, action and safe return destination. A public attempt ID is not possession proof. Nonce is cryptographically random and changes per attempt; only necessary verifiers/provenance are durable.
- [ ] Web pre-auth cookie/state and JSON credential exchange reject missing/wrong Origin, cross-site login, wrong binding and cookie duplication. GIS POST mode additionally needs its documented double-submit contract. No provider token in URL/history, SSR payload, localStorage or error output.
- [ ] Native chooser receives that attempt's nonce through a genuinely supported per-request API. Do not repeatedly initialize a singleton or reuse a consumed nonce. Test two successive sign-ins, cancellation/retry, logout/sign-in and account switch within one process; late chooser results cannot establish a session after cancellation/switch.
- [ ] Reviewed server library verifies signature, supported algorithms, fixed configured issuer/audience, applicable azp, expiry/time and nonce. Never trust client-decoded sub/email or token-directed key URLs. Key retrieval is bounded, cached, fixed-host, outside transactions; unavailable verification fails closed.
- [ ] After verification, short transaction rechecks attempt purpose/client/expiry/consumption, active account and version, provider uniqueness, then consumes attempt and issues existing app session atomically. Two processes racing the same attempt yield one success; two first-login attempts for one sub yield one user with defaults initialized once. Do not retry uncertain commits or overwrite existing preferences.
- [ ] Explicit linking requires current owner context and fresh proof of both identities. Cross-action sign-in token cannot link; provider already bound elsewhere is rejected. Same email alone never merges. Unlink and deletion prevent accidental last-method lockout and define whether/how a removed provider can create a new account; no silent provider-restore resurrection.
- [ ] Reader role only, mfaVerifiedAt remains null, no staff capability from Google/Workspace/Console ownership. Suspended/deleting/deleted and version-revoked accounts denied through real protected routes after exchange.
- [ ] App credentials remain secure-stored/HttpOnly as appropriate, Google token transient. Auth epoch changes precede pending account requests; queued storage/cache writes and old responses cannot restore the prior account after logout/switch. SDK sign-out does not remove the device Google account or revoke unrelated services.

### Additive migration and Profile privacy

- [ ] Inspect actual migration profile/pins immediately before writing; preserve old checksums. Attested backup → restored disposable clone → upgrade/rollback-recovery → preservation comparison precedes retained mutation. No retained DB mutation was authorized to this reviewer.
- [ ] Provider subject uniqueness, ownership FKs, session method constraints and last-method checks hold under concurrent transactions. New SECURITY DEFINER functions have fixed search_path, schema-qualified objects, narrow grants, PUBLIC revoked and no caller-supplied user context trust. Verify through non-owner roles.
- [ ] Profile DTO exposes only permitted owner data. Keep user display override separate from provider suggestion and email provenance; explicit input schemas disallow role/status/assurance mass assignment. Optimistic revisions preserve drafts on409 and account changes.
- [ ] Session list excludes bearer/hash/CSRF secrets; truthful current device labels, owner-scoped revocation and fresh proof for sensitive operations. Exports are owner-only, bounded and cleaned up; omit Google sub/token and private editorial/source payloads. Avoid exports while holding account locks.
- [ ] Disposable-user deletion invalidates sessions and required member data under documented retention; late listening writes cannot resurrect cleared history. Existing listening operation epoch tests must remain passing.
- [ ] Initials are safe default avatar. Any provider avatar integration has explicit URL/host/cache/privacy policy, never an unrestricted server image proxy or arbitrary third-party loading from user-supplied fields.
- [ ] Optional native email code is independently bounded: keyed verifier, atomic failed-attempt count/consumption, challenge/purpose/client binding, resend invalidation/quota, uniform responses. Captured mailbox is local proof only, not ownership of a real address or authorization to send external email.

### Live-source egress, permissions and public projection

- [ ] Fixed source-ID adapter config, no public arbitrary-URL fetching. Validate HTTPS scheme, no userinfo, allowed port/host/path; block local/private/link-local/metadata/special-use addresses including IPv4-mapped IPv6 and alternative encodings. Test the actual selected connection address, not URL syntax alone.
- [ ] Resolve all destination answers safely and pin approved connection resolution with TLS/SNI/hostname validation intact. Recheck every redirect and deny credential forwarding. Bound redirect count, deadlines, compressed/decompressed bytes, types and retries. Do not add a general localhost bypass to production source fetching for tests.
- [ ] Publisher requests use an isolated header set/client: no cookies, Authorization from users, Google tokens, email, internal IDs or secret referrers. Google fixed-key egress is a separate boundary, not publisher allowlist wildcard.
- [ ] Reject XXE/DTD, hostile HTML/scripts, truncation, oversized expansion and parser exhaustion; source text is inert data. Exact evidence offsets correspond to recorded normalized transformations/version. News-provided allowed:true/byline/content-kind cannot set trusted policy.
- [ ] Rights come from reviewed current terms plus item exceptions, with checked time, scope, attribution, retention and expiry. API/RSS availability is not a licence; primary agency reporting is not independent corroboration. No provider permission is verified by this document.
- [ ] Conditional304 preserves content/publication dates and still rechecks rights;429 respects bounded Retry-After; restart/idempotence and A→B→A observations remain durable. Withdrawal/expiry invalidates Home/search/edition/save projection, with lawful tombstone rather than fallback fiction.
- [ ] Publisher-original/metadata lanes are service-controlled and structurally separate from private extractive drafts. Neither license nor a Google reader session confers editorial approval. Anonymous SSR and complete relevant attribution remain; private evidence stays inaccessible.
- [ ] Sample/live separation survives errors and restart; real stories cannot resolve to unrelated prepared media. Preserve all23 renditions/93 original hashes. Conservative topic/entity classification cannot invent coverage.

## First implementation source review — unapplied migration 0013

Reviewed current packages/db/migrations/0013_google_reader_profile.sql, packages/domain/src/google-identity.ts and apps/api/src/google-auth-http.ts, with existing preflight/member identity code for context. **Source-only; SQL, HTTP, concurrency, provider and device tests NOT RUN.** The migration was reported not yet applied. These findings concern this inspected revision and must be rechecked after repairs.

### Findings requiring repair or an explicit narrower capability

1. **High: linking accepts local-only proof as real account continuity.** start_google_attempt accepts any authenticated recent authorizing session; finish_google_attempt rechecks its owner/version/age but neither rejects fixture/fixture-only nor captured-mail/local-demo. Consequently a locally claimable example.test account can be linked to a real Google subject and receive provider-verified sessions for its existing user row. This is not automatic email merging, but it still elevates fixture mailbox ownership through the link path without real proof of the pre-existing identity. The runbook explicitly prohibits that elevation. Require an independently supported real ownership proof, or reject local-only linking and present the safe recovery limitation. Test both fixture and captured-mail linking attempts, not only same-email sign-in separation.

2. **Medium: reauthentication cannot refresh an older session.** Both SQL start and finish require created_at within15 minutes for all non-sign-in actions. An otherwise active Google session older than15 minutes therefore cannot start reauthentication even though the purpose is to establish fresh proof. Separate permission to initiate reauthentication from proof required to link/unlink/revoke sensitive state; verify the same provider subject and current account/version, then issue a new recent session only after fresh provider proof. Test just-inside/outside freshness boundaries and an older valid session. Do not remove freshness requirements from linking as a shortcut.

3. **Medium: Profile session list overstates active sessions.** reader_profile filters only revoked_at and expires_at. It includes idle-expired sessions and sessions invalidated by account session_version changes, despite IdentityService rejecting them. Either exclude these or provide truthful inactive labels/status; sensitive session actions must independently enforce owner/recent proof. Test expired-idle and mismatched-version sessions.

4. **Low hardening: native link/reauth header parity.** Google native start parses req.get('Authorization') without the member router's raw-header exactly-one check. Duplicate Authorization headers should be rejected explicitly rather than relying on Node/header normalization. Native sign-in already rejects any Authorization and every exchange/cancel rejects it; retain those boundaries. This is a contract inconsistency, not demonstrated authentication bypass in this source-only pass.

5. **Time-of-check edge to cover:** finish_google_attempt captures moment before advisory/account lock waits and uses it for originating session expiry/recentness; only attempt expiry is checked against fresh clock time immediately before issue. Revalidate originating-session validity with current database time after locks, including idle expiry and permitted proof, before issuing a replacement. A bounded lock timeout limits delay but does not eliminate a near-expiry acceptance boundary. No timing exploit was executed.

### Positive source observations, not test passes

The new sign-in path resolves canonical provider+subject and creates a user without email lookup/upsert, preserving existing email accounts. Advisory serialization per subject and final attempt row lock aim to handle concurrent first registration and one-time consumption. The HTTP wrapper throws on false finish results inside its transaction, so preparatory writes are rolled back rather than returned as success; preserve that contract for any future caller. Successful issuance is returned after unit.run commits. Domain and member DTO method/assurance unions now include Google and retain null MFA/reader capability limits.

Google token verification runs after an autocommit attempt lookup releases its connection and before the write unit of work. It uses the official library, rejects non-RS256/token-directed keys, checks fixed audience/allowed issuer/nonce/time and configured azp, and replaces library errors with a fixed category. This review did not inspect installed library internals or verify its network/cache behavior; claimed bounded key retrieval still needs dependency/source and test verification. Binding/action lives in the stored attempt, and cancellation is rechecked under final locking; nonce values are generated afresh by the server. Native actual chooser nonce delivery is outside these three files and remains unverified.

The new pre-auth web path retains exact Origin and preflight cookie-hash CSRF binding; new native paths reject browser cookies/Origin. Profile returns provider email claims, not raw token/sub, and display-name edits use a revision predicate. The profile query remains unbounded in session count, and existing rate/retention behavior plus sensitive export/revoke/unlink endpoints require their own subsequent review. None of these observations grants acceptance of the new migration or real Google integration.
